## Behaviours that differ from the webview

1. **`ui.locale()`**: the webview calls `commands.pluginSetUiLocale(LOCALES[locale].tag)` whenever its locale changes (`src/features/app/locale.ts:20`); the native app never calls `PluginHost::set_ui_locale`, so plugins always read `"en"`. `settings_model::runtime::runtime_settings` computes `language_tag` and nobody reads it (grep `language_tag` finds only its definition). The contained part of the fix, in `app-gpui/src/plugins.rs` `Plugins::init`, after `projects.set_plugin_host(&host);`:
   ```diff
            projects.set_plugin_host(&host);
   +        // Plugin code reads the UI language with `ui.locale()`.
   +        host.set_ui_locale(cx.default_global::<crate::platform::i18n::Localization>().0.locale_info().tag);
   ```
   Following a later change of `appearance.locale` needs the place where the app applies that setting to `Localization`, which I did not find (no non-test `set_locale(` call in `app-gpui/src`): it may not be built. No test written (needs the fixture and the feature).
2. **`editor.open-editors`**: the webview's MCP feature reports the window's open editors with `commands.mcpSetOpenEditors(paths)` (`src/features/mcp/index.ts:59` → `mcp_set_open_editors` → `mcp_reports.set_open_editors`), and `HostWorkspace::open_editors` answers plugins from that report (`api.rs:2826`). app-gpui never reports them (it calls only `mcp_reports.report_problems`, `workbench/code_insight.rs:592`), so a plugin lists no editors; the MCP server's own editor tools (`ide-host/src/mcp/editors.rs`) read the same empty report. `proofs10_host_api::a_plugin_lists_the_windows_open_editors` is expected to fail. Contained fix in `app-gpui/src/workbench/plugin_runtime.rs`, `plugin_tabs_changed`, which already computes the window's open files:
   ```diff
            let opened: Vec<String> = open.difference(&self.plugin_runtime.open_files).cloned().collect();
            let closed: Vec<String> = self.plugin_runtime.open_files.difference(&open).cloned().collect();
   +        // Plugin code and the MCP server list the window's editors from this report.
   +        if (!opened.is_empty() || !closed.is_empty())
   +            && let Some(backend) = cx.try_global::<Backend>()
   +        {
   +            backend.host.mcp_reports.set_open_editors(&self.label, open.iter().map(PathBuf::from).collect());
   +        }
            self.plugin_runtime.open_files = open;
   ```
   (The focused editor, `OpenEditor::active`, is `mcp_set_focused_editor` in the webview; the same place could call `set_focused_editor` with the active path, whose `FocusedEditor` shape I did not read. The listener guard at the top of `plugin_tabs_changed` returns early in a window without a plugin host, where nobody asks.) Check whether `ipc:mcp_set_open_editors` has its own inventory row before claiming it.
3. Nothing else found to differ among the functions tested: the command-request projection (`runtime_ui::command_request`) matches the webview's (declared commands first, then actions, else not found); the menu argument `{ path, paths }` is unpacked as the webview's `executeAction` passes it.

- **Consent for a running plugin's permission request** (`point.registerOverlay:plugins.consent`, `ipc:plugin_grant`): `ConsentRequested` is emitted only when a live plugin has `pending` capabilities (`ide-host/src/plugins/mod.rs:1452`), which `ledger.decide` produces only for a grant migrated from API 0.1 (`Decision::Allowed { pending }`). No fixture or helper creates such a ledger entry; a test needs a ledger file written in the 0.1 format before the host starts, whose layout I did not read. The dialog side (`plugins_window.rs:381` → `show_consent` → `grant_asked`) is served.
- **storage.keys, output.clear, secrets.is-set, child.poll/write/kill**: served, but no checked-in fixture calls them; each needs a fixture command (e.g. api14 `"keys" => Ok(Some(host::storage::keys("")?.join(",")))`) and a rebuild. Not written.

- **vcs.remotes** (jobs `remotes`): needs a remote; a bare repository in a temp dir added as `origin` would do. Not written: counted served-but-untested.
- **ipc** (api14 `ipc`, a Unix socket matching `$TMPDIR/api14-*`) and **auth** (api14 `oauth`, a localhost loopback): served host-side; both need a peer the test runs (a socket echo thread; an HTTP request to the redirect URI). Not written: counted served-but-untested.

## Tests most likely to fail first

0. Expected failures by design: `a_plugin_lists_the_windows_open_editors` (difference 2), `a_plugin_reads_the_ui_language_the_settings_choose` (fixture + difference 1), `turning_a_running_plugin_off_runs_its_deactivate` (fixture).
1. `a_plugin_on_a_schedule_runs_when_its_period_is_over`: `tick_at` queues `scheduled` only while the plugin is `Inactive` with nothing pending and after `startup_finished` (set 1.5 s after the host starts, `plugins.rs:223`; the project opening takes longer, but the test ticks on every poll, so a late startup only delays it). The scheduled handler fetches first; in a repository without remotes `fetch` may fail and post "Git Toolbox: fetch failed" (harmless) before `show` sets the item.
2. `a_file_created_on_disk_reaches_the_plugin_as_files_changed`: `post_files_changed` delivers only while the project's `files_events_active` is set and the host maps the window `w1` to the project (`files_changed.rs:86`); if the flag follows subscriptions known only after the first listing, the single write may come too early. Fix in the test if so: write a second file inside the wait every few hundred polls.
3. `a_file_whose_tab_closes_reaches_the_plugin_activated_by_file_closed`: the stored `data` shape of `file-closed` (assumed a string containing the path).
4. `a_status_item_the_plugin_removes_leaves_the_status_bar`: after `.git` is removed, `vcs_status` must answer `None` (git-toolbox then calls `remove_status_item`); an error instead makes `refresh` fail with the item left.
5. `turning_a_running_plugin_off_runs_its_deactivate`: fails until api14 is rebuilt (by design). Also assumes the actor runs `deactivate` when the plugin is disabled (`ide-plugin/src/actor.rs:128` runs it when the actor loop ends) and that storage writes still work then.
6. `asks_multi_line_text_and_confirms_on_ctrl_enter`: Ctrl+Enter is read with `modifiers.control` (`prompt_dialog.rs:388`), so `ctrl-enter` works on every platform; the risk is the area's focus inside the workbench's prompt layer (the existing one-line test asserts it, so likely fine).
